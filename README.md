# 一、系统概述
      为了方便餐馆管理，相关数据的统计，以便于餐馆的营业，同时为餐馆扩展外卖订单的处理，设计了餐馆管理系统。
餐馆管理系统是一个基于Java Spring Boot框架开发的企业级管理系统，旨在为餐馆提供全面的数字化解决方案。系统采用现代化的微服务架构模式，使用MyBatis-Flex作为ORM框架，数据库使用MySQL，并集成Redis缓存以提高系统性能。

该系统不仅涵盖了餐馆日常运营的核心业务功能，还包括完善的后台管理系统，支持多角色用户权限控制、数据统计分析、库存管理等高级功能。该系统可适用于餐馆营业方面，方便餐厅工作人员的使用，更加可视化。系统设计遵循高内聚低耦合的原则，具有良好的可扩展性和可维护性。
系统用户主要为餐馆的管理人员，负责对餐桌、菜品等的相关管理，对于客户点单（堂食订单和外卖订单）、菜品制作进度、客户催单的相关处理功能。极大的方便了对于餐馆的管理，增强了工作的交互性，提高了效率。
# 二、需求分析
## 2.1系统功能分析
系统主要包含以下功能模块：

- 菜品管理
- 餐桌管理
- 堂食管理
- 外卖管理
- 原材料管理
- 费用管理
- 查询统计
- 用户权限管理
- 异常处理
## 2.2系统数据分析
### 2.2.1 系统对数据的需求
系统的数据需求源于其业务目标和功能模块，主要体现在以下几个方面：
1.	业务操作数据需求：
•	记录菜品的详细信息（名称、价格、配方等）以供展示和销售。
•	记录订单的完整生命周期（创建、支付、完成、退款）以实现流程跟踪和财务管理。
•	记录餐桌的实时状态以支持高效的座位安排和翻台。
•	记录库存的出入库和当前存量以实现成本控制和预警。
•	记录各项费用支出以进行财务核算。
2.	统计分析数据需求：
•	聚合订单数据，分析销售趋势和热门菜品。
•	计算成本（食材消耗）和收入（订单金额），分析利润情况。
•	统计费用支出，分析成本构成。
3.	系统管理与安全数据需求：
•	存储用户凭证和权限信息，用于身份认证和访问控制。
•	维护角色和权限的映射关系，实现灵活的权限管理。
### 2.2.2 系统中需要保存的数据
系统需要持久化保存的数据实体主要包括三大类：
1. 核心业务实体：
•	菜品 (Dish)：菜品ID、名称、分类、价格、图片、描述等。
•	订单 (Orders)：订单ID、订单号、类型（堂食/外卖）、总金额、状态、支付信息、时间等。
•	订单详情 (OrderDetail)：详情ID、所属订单ID、菜品ID、菜品名称（快照）、数量、金额等。
•	堂食订单 (DineInOrders)：ID、关联订单ID、餐桌ID、客人数量、备注等。
•	外卖订单 (TakeawayOrders)：ID、关联订单ID、顾客信息（姓名、电话、地址）、配送费用、备注等。
•	餐桌 (DiningTable)：餐桌ID、编号、容量、状态（空闲/占用/预订）等。
•	费用 (Expense)：费用ID、类别、金额、日期、描述等。
2. 资源与关联实体：
•	库存 (Inventory)：材料ID、名称、当前库存量、最低库存预警值、单位、状态等。
•	菜品配方 (DishRecipe)：配方ID、菜品ID、材料ID、所需材料数量、单位等。（此表是Dish和Inventory之间的关联表）
3. 系统管理实体：
•	系统用户 (SysUser)：用户ID、用户名、密码、昵称、手机号、账户状态等。
•	角色 (SysRole)：角色ID、角色名称、角色标识符、状态等。
### 2.2.3 数据之间的联系
系统中的数据不是孤立的，它们通过主外键关系相互关联，形成一个完整的业务数据模型，主要联系如下：
1.	订单核心关系链：
•	Orders1 : N OrderDetail一个订单包含多个菜品明细，通过OrderDetail表中的order_id关联。
•	OrderDetailN : 1 Dish一个订单明细对应一个菜品，记录菜品ID (dish_id) 和快照信息。这是一种弱关联，允许菜品信息变更后仍能追溯历史订单详情。
•	Orders1 : 1 DineInOrders/ TakeawayOrders一个订单要么扩展为一条堂食记录，要么扩展为一条外卖记录，通过order_id进行一对一关联。这体现了继承关系，使用“表具体化”模式实现。
2.	资源消耗关系链：
•	Dish1 : N DishRecipe一道菜品可以由多种食材构成（一个菜品对应多个配方记录）。
•	DishRecipeN : 1 Inventory一个配方记录对应一种库存材料，通过material_id关联。DishRecipe表作为关联表，定义了Dish和Inventory之间的多对多关系，并记录了关联的量化属性（所需数量）。
•	业务逻辑关联：当订单完成时，系统会根据订单中的菜品 (Dish)，找到其配方 (DishRecipe)，然后扣减相应食材的库存 (Inventory)。
3.	餐厅运营关系：
•	DineInOrdersN : 1 DiningTable一个堂食订单对应一个餐桌，一个餐桌在不同时间段可以对应多个订单。通过table_id关联。

## 2.3系统非功能分析
1.	性能：系统能支持多用户并发访问，响应时间不超过3秒。
2.	安全性：系统具备用户身份验证，采用基于Sa-Token的认证机制，支持多因素认证权限控制功能。基于角色的权限控制（RBAC），实现菜单权限和数据权限的双重管控。支持会话超时自动退出，防止会话劫持。
3.	可扩展性：系统具备良好的可扩展性，便于后续功能扩展。采用高内聚低耦合的设计原则，各功能模块独立可替换。具备完善的日志记录功能，支持问题排查和性能分析。提供标准化RESTful API接口，便于第三方系统集成
4.	可用性：系统提供良好的用户体验。采用直观的界面设计，符合餐厅业务操作习惯。操作简便，业务流程设计简洁，减少不必要的操作步骤。
# 三、系统设计
## 3.1应用程序设计
系统架构
系统采用前后端分离的架构模式：
 
后端技术栈
核心框架：Spring Boot 3.5.3
编程语言：Java 21
ORM框架：MyBatis-Flex 1.11.0
权限认证：Sa-Token 1.44.0
数据库：MySQL 9.3.0
缓存：Redis
API文档：Knife4j 4.5.0
JSON处理：Jackson 2.19.1
工具库：Lombok 1.18.38, Apache Commons系列
构建工具：Maven
前端技术栈
核心框架：Vue 3 (v3.5.13)
路由管理：Vue Router (v4.5.1)
状态管理：Pinia (v2.3.1)
UI组件库：Element Plus (v2.9.9)
构建工具：Vite (v6.3.4)
语言：TypeScript (v5.2.2)
HTTP客户端：Axios (v1.9.0)
样式处理：Sass
代码质量：ESLint + Prettier
前后端关系
前后端通过RESTful API进行通信，采用JSON格式交换数据。前端通过Axios向后端发送HTTP请求，后端接收请求并返回相应的JSON数据。认证授权通过JWT Token实现，前端在每次请求时携带Token进行身份验证。
系统模块及模块关系
模块详细说明
1.	餐厅管理模块 (restaurant)
a)	菜品管理：管理餐厅的菜品信息
b)	餐桌管理：管理餐厅的餐桌信息
c)	库存管理：管理餐厅的库存信息
d)	支出管理：管理餐厅的支出记录
e)	菜谱管理：管理菜品的制作配方
2.	订单管理模块 (order)
a)	堂食订单：处理顾客在餐厅内用餐的订单
b)	外卖订单：处理外卖配送的订单
c)	客户订单：提供给访客的自助下单功能
3.	系统管理模块 (system)
a)	用户管理：管理系统用户账户
b)	角色管理：管理系统角色及权限
c)	数据权限：管理数据访问权限
d)	字典管理：管理系统数据字典
4.	统计分析模块 (statistics)
a)	销售统计：统计餐厅的销售数据
b)	利润分析：分析餐厅的盈利情况
c)	菜品排行：分析菜品的销售排行
